# 建库日志与数据质量记录

这份文档是 ARCHITECTURE.md 和 README.md 里**非压测类数字的出处**（压测数字的出处是 [BENCHMARK.md](BENCHMARK.md)）。
每一节都写明数据是怎么得到的：

- **〔日志〕** 直接抄自 `build_index` 的结束日志和 `/usr/bin/time -v`，可以用同样的语料和提交重跑复现；
- **〔一次性分析〕** 来自当时写的临时分析脚本（没有入库），只能按文中描述的方法重做，不能一键复现；
- **〔无留存〕** 当时测过但没有留下原始记录，数字只能当作量级参考。

除特别注明外，机器都是 BENCHMARK.md 第 1 节那台 4 核 ARM64 服务器，`build_threads = 2`，`nice -n 10`。

## 2. SimHash 误判的诊断与修复（第四阶段 B2）

### 2.1 现象〔一次性分析〕

L3 这次建库里，中文 20 万篇被丢弃 4,886 篇，其中 107 篇“匹配”到的是英文的 Stack Overflow 提问。
把被丢弃文档和它匹配到的文档成对导出，逐对看词频：

| 被丢弃的文档 | 匹配到的文档 | 海明距离 | 主导词 |
| --- | --- | --- | --- |
| 山田泰宽（足球运动员，38 个词项） | R 语言提问 "convert a row of a data frame…"（48 个词项） | 1 | "0"：30 次（占全文 34.5%）对 18 次（23.1%） |
| 佃贤典（17 个词项） | 同上 | 1 | "0"：34 次，占 54.0% |
| 有线电视剧集台电视剧集列表（81 个词项） | "ipmitool gives Authentication type NONE…" | 3 | "00"：107 次对 104 次 |
| 王绘春（演员，121 个词项） | 家变 (1977年电视剧)（915 个词项） | 2 | "饰"：28 次对 93 次 |
| 美国国家科学院（375 个词项） | 6月28日（1,063 个词项） | 1 | "年"：146 次对 187 次 |

无关配对里“出现最多的那个词占全文的比例”中位数是 12.4%，全体中文文档是 5.4%。
最后两行说明问题不限于短文档。

### 2.2 四种方案的对比〔一次性分析〕

同一份 120 万篇语料（L3），只改指纹的算法：

| 指标 | 原始词频（修复前） | **`1 + log2(tf)`（采用）** | `sqrt(tf)` | 原始词频 + 少于 100 个词项的文档只做精确去重 |
| --- | --- | --- | --- | --- |
| 英文 100 万篇丢弃 | 6,229 | 120 | 134 | 2,779 |
| 中文 20 万篇丢弃 | 4,886 | 1,759 | 2,351 | 1,960 |
| 其中匹配到英文文档 | 107 | 0 | 1 | 65 |
| 模拟语料 2 万篇里 1,010 篇转载的丢弃数 | 982 | 948（实际建库 945） | 918 | 916 |
| 模拟语料非转载被丢弃 | 0 | 0 | 0 | 0 |
| RSS 样例入库（读入 4,208） | 3,923 | 3,941 | 3,944 | 3,950 |

中文被丢弃的文档随机抽 400 对，按“正文字符二元组的 Jaccard 相似度”自动分类
（≥ 0.9 且标题相同 = 真重复；≥ 0.8 = 模板化；0.2~0.8 = 同模板不同内容；< 0.2 = 无关）：

| 类别 | 原始词频 | `1 + log2(tf)` | `sqrt(tf)` | 短文档只精确去重 |
| --- | --- | --- | --- | --- |
| 真重复 | 0 | 0 | 0 | 0 |
| 模板化（正文近乎相同） | 45.0% | 92.0% | 90.0% | 10.8% |
| 同模板不同内容 | 31.0% | 8.0% | 9.8% | 42.8% |
| 无关 | 24.0% | **0%** | 0.2% | 46.5% |

- 2.1 表里匹配到 Stack Overflow 的 9 对，换成 `1 + log2(tf)` 后海明距离从 1~3 变成 18~32。
- 英文剩下的 120 篇抽查 8 对，都是同一个问题被问了两次
  （例如 "Mask VisualEffect blur with drawn image" 与 "Mask blur with image"）。
- 表中“948”是分析脚本算的，“945”是真正用 `build_index` 建库的结果；两者差 3 篇，原因没有追查。

## 5. 线上部署的实测（第四阶段 C）〔日志：journald 与 `systemctl status`〕

| 项目 | 值 |
| --- | --- |
| 启动耗时（journald：`config loaded` 23:53:24 → `listening` 23:53:28，页缓存是冷的） | 约 4 s（其中加载 198 万词的联想词典、构建 Trie 约 3 s） |
| 预读耗时（启动前先用 `posix_fadvise(DONTNEED)` 把索引文件逐出页缓存） | 131.4 s（5.50 GiB，约 43 MiB/s） |
| 预读完成后 `systemctl status` 的 Memory | 5.8G（`memory.current` = 6,243,577,856 字节） |
| 其中文件页 / 匿名页（`memory.stat`） | 5,805,232,128 / 435,494,912 字节 |
| 进程 `VmRSS`（RssFile / RssAnon） | 6,091,136 KB（5,665,848 / 425,288） |

结论：`mmap` 的索引占用的页缓存**计入**服务自己的 cgroup，所以 `MemoryMax` 要按“索引大小 + 进程自身内存”来留。
