# 压测报告：search_server（含 C10K）

测试日期：2026-11-12，代码版本 `a57b73a`。本文只写实际测到的数；凡是没有直接证据的解释都标了 **（推测）**。

## 结论速览

1. **命中缓存时，2 个核能跑到约 3.6~3.8 万 QPS**，瓶颈是服务端 CPU（两个核都在 195% 以上），与连接数基本无关。
2. **纯检索计算约 4,600~4,700 QPS（2 核）**，同样是 CPU 打满；连接数从 10 加到 500，吞吐不变，延迟随排队线性增长。
3. **连接数的三道闸是真实存在的，而且失败方式各不相同**：fd 上限让多出来的连接无声地卡在 accept 队列里；`max_connections` 让服务端主动断开连接，吞吐掉到原来的 1/5。
4. **三道闸全部放开后，20,000 个并发连接零错误**，吞吐仍是 3.5 万 QPS，每个连接约占 6 KB 用户态内存。
5. **索引不在页缓存里时，未命中查询慢两个数量级**（p50 约 130 ms 对 0.4 ms）。部署后的第一批查询会遇到这个问题。

### 绑核与网络路径

- `search_server` 用 `taskset -c 2,3` 固定在 2 个核上，`wrk` 用 `taskset -c 0,1` 固定在另外 2 个核上，避免互相抢 CPU。
- **客户端和服务端在同一台机器上，走 loopback（127.0.0.1）**。没有真实网卡、没有网络延迟和丢包。
- 所以下面所有"CPU%"的满值是 **200%**（2 个核）。

### 服务端的线程模型

Workflow 的网络线程和计算线程数都用默认值，没有调过；它们全部被限制在核 2、3 上。

## 2. 方法与命令

全部测试由一个脚本驱动，结果写到 `build/bench/<时间戳>/results.tsv`：

```bash
python3 scripts/bench/gen_queries.py            # 生成查询集（种子 42，可复现）
scripts/bench/run_bench.sh                      # 全部阶段
scripts/bench/run_bench.sh baseline scale       # 只跑指定阶段
BASE_CONF=conf/oracle.conf scripts/bench/run_bench.sh c10k-tuned
```

每一轮实际执行的命令形如：

```bash
# 服务端
( ulimit -n 65535; exec taskset -c 2,3 ./bin/search_server conf/bench-cache.conf )
# 客户端
( ulimit -n 65535; exec taskset -c 0,1 wrk -t2 -c100 -d30s --latency \
    -s scripts/bench/search.lua http://127.0.0.1:9000 -- scripts/bench/queries.txt )
# 采样
pidstat -h -u -r -p <server_pid> 1 30           # 每秒一次 CPU% 和 RSS
ss -s; ss -Htn state established '( sport = :9000 )' | wc -l    # 压测进行到一半时
```

要点：

- **每轮 30 秒，轮间隔 10 秒**；单连接基线每轮 10 秒。
- **两份配置**：`bench-cache.conf`（`cache_capacity = 20000`，默认值）和 `bench-nocache.conf`（`cache_capacity = 0`）。容量为 0 时 `LruCache::put` 直接返回，`get` 查的是空表，相当于关闭缓存。
- **wrk 脚本**：`search.lua` 每个请求随机选一条查询并做 URL 编码；`recommend.lua` 取查询的前 2~4 个字母。两个脚本都在 `response()` 里统计非 2xx 响应，在 `done()` 里汇总。
- **页缓存预热**：脚本开始时把索引文件顺序读一遍（`cat > /dev/null`）。原因见 6.5 节。
- **C10K 阶段每个连接数档位都重启服务并重新预热 30 秒**，这样 RSS 有干净的起点。
- **没有修改任何 sysctl**。本机的 `net.core.somaxconn = 32768`、`net.ipv4.tcp_max_syn_backlog = 16384` 已经足够大。

### 三个场景

| 场景 | 配置 | 查询 | 测的是什么 |
| --- | --- | --- | --- |
| A 命中缓存 | cache | 固定一条 | 网络层和框架本身的上限 |
| B 纯计算 | nocache | 随机 | 检索算法的上限 |
| C 真实混合 | cache | 随机，先预热 30 秒 | 见下面的说明 |

**场景 C 的局限**：查询集只有 4,741 条不同的查询，小于缓存容量 20,000。预热之后所有查询都在缓存里，所以场景 C 实际上是"几乎 100% 命中、但 key 分散在 16 个分片上"，而不是真正的冷热混合。

## 5. C10K：连接数扩展

场景 C，`wrk -t2 -d30s`。四组配置的区别只在三个开关：

| 组 | 服务端 `ulimit -n` | wrk `ulimit -n` | `max_connections` |
| --- | --- | --- | --- |
| ① 默认 | 1024 | 1024 | 2000 |
| ② 只限服务端 fd | 1024 | 65535 | 2000 |
| ③ 只限 max_connections | 65535 | 65535 | 2000 |
| ④ 三道闸全开 | 65535 | 65535 | 20000 |

第三道闸（内核的 `somaxconn` / `tcp_max_syn_backlog`）在本机已经是 32768 / 16384，四组都没有动它。

> **后续改动**：本节测的是提交 `a57b73a`，当时 fd 上限不够只打印告警。针对第 ② 组暴露的无声故障，之后的版本改为：
> 启动时自动把 fd 软上限提到 `max_connections + 64`，硬上限也不够则拒绝启动。所以第 ①、② 两组在新版本上已无法复现
> （服务会直接报错退出）。验证：软上限 1024、`max_connections = 5000` 时，服务把软上限提到 5,064，
> 3,000 个并发连接下服务端 fd 为 3,021、accept 队列为 0、零错误。

表里的"内核已建立"是 `ss` 看到的服务端一侧的已建立连接数，**它包含已经完成握手、但服务进程还没 `accept()` 的连接**。"服务端 fd"是 `/proc/<pid>/fd` 里的条目数，"accept 队列"是监听 socket 的 Recv-Q。三者都在压测进行到第 15 秒时采样。

| --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 34,096 | 29.1 | 44.2 | 0 / 0 / 0 / 0 | 0 | 1,000 | 1,694 |
| 2,000 | 29,085 | 33.7 | 54.4 | 981 / 0 / 0 / 0 | 0 | 1,019 | 1,696 |
| 5,000 | 29,401 | 33.1 | 50.7 | 3,981 / 0 / 0 / 0 | 0 | 1,019 | 1,693 |
| 10,000 | 29,042 | 34.1 | 43.2 | 8,981 / 0 / 0 / 0 | 0 | 1,019 | 1,695 |

- **从 2,000 连接开始出错，错误类型全部是 connect。** 错误数恰好是"连接数 − 1,019"：先撞墙的是 **wrk 自己**，它在 fd 上限 1024 下只开得出 1,019 个 socket。
- 服务日志每次启动都有一条告警：`fd limit (ulimit -n = 1024) is lower than max_connections (2000)`。除此之外日志里没有任何错误。

这一组说明不了服务端的问题，所以加了第 ② 组。

- **服务进程的 fd 停在 1,024，多出来的连接全部卡在 accept 队列里。** 2,000 连接时有 997 个、5,000 连接时有 3,997 个连接完成了握手却始终没人服务。
- **这种失败是无声的**：wrk 报告 0 错误，服务日志也没有任何输出。只有 p50 暴露了问题：它停在 34 ms，和 1,000 连接时一样，说明真正在被服务的连接只有 1,000 个左右。
- **到 10,000 连接时 accept 队列也满了**（4,097，Workflow 以 backlog 4096 监听），内核开始丢弃新连接，30 秒内丢了 14.7 万次，wrk 出现 44,100 个 write 错误。

## 6. 瓶颈分析

### 6.1 场景 A（命中缓存）：服务端 CPU，开销在网络层和框架

- **依据**：服务端 CPU 195%~198%（满值 200%），而 wrk 只用了 80%~85%，客户端还有余量。QPS 在 50 连接以上就稳定在 3.6~3.8 万，再加连接只增加排队时间。
- 折算下来每个请求约消耗 52 µs 的服务端 CPU（2 核 ÷ 3.8 万）。
- **不是缓存锁**：场景 A 所有请求打在同一个 key、同一个分片的同一把锁上，QPS 是 3.8 万；场景 C 的 key 分散在 16 个分片上，QPS 是 3.6 万。如果锁是瓶颈，A 应该比 C 慢，实际 A 更快。
- 这 52 µs 具体花在内核网络栈、HTTP 解析还是框架调度上，**本次没有做 profiling，无法区分**。

### 6.2 场景 B（纯计算）：服务端 CPU，开销在检索计算

- **依据**：服务端 CPU 199%，wrk 只用了 18%。QPS 从 10 连接到 500 连接都是 4,600~4,700，p50 从 1.9 ms 涨到 108.6 ms，完全是排队。
- 折算每个查询约消耗 0.43 ms 的 CPU（2 核 ÷ 4,700），与单连接基线的 p50（0.43 ms）吻合。
- 命中缓存比现算快约 8 倍（3.8 万对 4,700 QPS）。

### 6.3 场景 C（混合）：预热后等同于场景 A

- 预热后全部命中，QPS 比场景 A 低约 5%（3.6 万对 3.8 万）。**（推测）** 差距来自随机 key 的缓存局部性更差，以及 wrk 一侧随机选查询的开销（wrk CPU 从 82% 升到 92%）。
- 这个场景没有测出"部分命中"时的表现，原因见第 2 节。

### 6.4 C10K：瓶颈是连接上限，放开之后回到 CPU

- **fd 上限**和 **`max_connections`** 是两道独立的闸，各自的证据见第 5 节的 ②、③ 两组。
- **内核队列**这道闸在本机没有成为瓶颈：第 ④ 组 20,000 连接时监听队列丢弃数为 0。
- 全部放开后，1,000 到 20,000 连接的 QPS 都在 3.1 万~3.5 万，服务端 CPU 196%：**连接数本身不是瓶颈，瓶颈回到了 CPU**。

### 6.5 页缓存：冷启动时未命中查询慢两个数量级

调试脚本时意外测到的，不是受控实验（没有执行 `drop_caches`），数字仅供参考：

| 页缓存状态 | `/search` 未命中，单连接 10 秒 | 服务端 CPU |
| --- | --- | --- |
| 冷（建库约 40 分钟后首次压测） | 8.1 QPS，p50 130.6 ms，p99 372.8 ms | 6%，每秒约 96 次主缺页 |
| 部分预热（紧接着第二次） | 72 QPS，p50 15.3 ms，p99 131.3 ms | 6% |
| 预热后（`cat` 过一遍索引） | 1,783 QPS，p50 0.43 ms，p99 8.7 ms | 87% |

- 索引是 `mmap` 的，"启动只要 1 秒"的代价是数据在第一次被查到时才从磁盘读入。冷的时候服务端 CPU 只有 6%，时间都花在等磁盘上。
- 所以本次所有正式测试都先把索引读进了页缓存。

#### 受控实验：`preload_index` 的效果

上表之后，代码里加了 `preload_index` 配置项（启动后用后台线程把索引顺序读进页缓存），并做了一次受控实验：

```bash
python3 scripts/bench/cold_start.py --base-conf conf/oracle.conf --cpus 2,3
```

每一轮先用 `posix_fadvise(POSIX_FADV_DONTNEED)` 把三个索引文件（共 1,730 MiB）逐出页缓存，用 `mincore()` 确认驻留比例为 0%，
再启动服务，就绪后用一个连接顺序发 300 条互不相同的查询（全部未命中）。这个逐出操作只作用于这三个文件，不是全机的 `drop_caches`。

| 配置 | 就绪 (ms) | 查询开始时索引驻留 | 前 20 条 p50 (ms) | 300 条 p50 (ms) | p90 (ms) | p99 (ms) | 最大 (ms) | 300 条查完 (s) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `preload_index = false` | 1,085 | 3.6% | 332.5 | 45.7 | 281.7 | 497.7 | 526.4 | 29.1 |
| `preload_index = true`，就绪后立刻查询 | 1,096 | 4.7% | 776.7 | 0.81 | 416.4 | 1,243.6 | 2,899.7 | 33.7 |
| `preload_index = true`，等预读完成（33.6 秒）再查询 | 1,086 | 99.4% | 0.50 | 0.52 | 1.20 | 5.98 | 41.1 | 0.28 |

- **预读不影响启动时间**：三种情况下服务都在 1.1 秒左右就绪。
- **预读读完整个索引用了 33.6 秒**，约 51 MiB/s，这是这块云盘的顺序读速度。读完之后，首批未命中查询的 p50 是 0.5 ms，与热状态一致。
- **预读进行中发起的查询反而更慢**：前 20 条的 p50 从 333 ms 升到 777 ms，最大值到 2.9 秒，因为查询的随机读要和预读线程抢磁盘。
  预读把"每个查询各等一次磁盘"换成了"先集中等 34 秒"。实际部署时，重启后的头半分钟最好不要把流量切过来。
- **不开预读时，页缓存也会被查询自己逐渐填满**：300 条查询跑完（29 秒）后索引驻留已到 89.8%，后面的查询越来越快，所以整体 p50 是 45.7 ms 而不是 333 ms。

**对整个文件调用一次 `madvise(MADV_WILLNEED)` 不起作用。** 这是最初的实现方式，实测对 495 MiB 的 `index.dat` 调用一次后，
驻留比例停在 0.8%（4 MiB），8 秒后也没有变化。Linux 把单次预读量封顶在块设备的 max(`read_ahead_kb`, `max_sectors_kb`)，
本机分别是 2,048 和 4,096 KB。按 256 KiB 分块调用能读进 100%，但调用本身会阻塞 8.8 秒。
所以最终实现是放在后台线程里，按 1 MiB 分块 `madvise` 再逐页读取。

## 7. 对线上服务的影响与系统改动

- **sysctl**：没有修改任何值。
- **容器**：每轮压测前检查，全程没有容器变成 unhealthy。压测前后 `docker ps` 的容器列表和状态完全一致，`docker stats` 里各容器的内存变化都在 20 MiB 以内。
- **安装的软件**：`wrk`（连带 `libluajit`）。

## 8. 测试的局限性

- **同机压测**：wrk 和服务端共用一台 4 核机器，各占 2 核。场景 A、C 里 wrk 自己用掉了 80%~110% 的 CPU，在 10 连接档位上客户端可能也是限制因素之一。
- **loopback**：没有真实网卡、没有延迟和丢包，网络部分的开销比真实部署低。
- **wrk 是闭环压测**：每个连接等上一个响应回来才发下一个请求。服务端一慢，客户端的发送速率也跟着降，所以测到的延迟比"固定到达速率"的真实流量乐观（coordinated omission）。C10K 表里的 p50 基本等于 连接数 ÷ QPS，反映的是排队，不是单个请求的处理时间。
- **只有 2 个核给服务端**：没有测 4 核或更多核时的扩展性，也就看不出锁竞争在更多核上会不会出现。
- **单机、单次**：每个档位只跑了一次 30 秒，没有重复取平均。第 ②、③ 两组跑过两次，两次的 QPS 相差在 5% 以内。
- **查询集偏小**：4,741 条不同查询小于缓存容量，场景 C 实际是全命中。
- **线上容器在同时运行**：有背景噪声。
- **wrk 的超时计数**：第 ② 组里有上千个连接整整 30 秒没有得到响应，但 wrk 报告的 timeout 是 0。读 wrk 的错误数时不能只看它是不是 0。
- **没有 profiling**：瓶颈分析基于 CPU 占用率和对照实验，没有火焰图。
